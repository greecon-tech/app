## A) Safety boundary and how to state it honestly
**Core concepts (public summaries)**
- Safe state: safety systems exist "to reduce the likelihood and/or consequence of ... hazardous situations by bringing the system to a safe state" (NIST SP 800-82r3 s2.3.7) [H]; defined per asset by hazard analysis (pump: stopped; some valves closed, others open), not by software convention.
- SIF/SIS: sensors + logic solver + final elements that drive the process to the safe state when thresholds are violated; an SIS follows IEC 61511 (derived from IEC 61508) and is "often independent from all other control systems" so a BPCS failure cannot defeat it (NIST s2.3.7) [H]. Integrity = SIL 1-4 (SIL1 = PFD 1e-2..1e-1 on demand) [M]; the safe state must be reached within the process safety time [M, Wikipedia "Safety instrumented system"]; IEC 61511-1:2016 added an SIS security risk assessment (cl. 8.2.4) [M, recalled].
- Fail-safe: OT "typically employ fail-to-a-known-state design"; lost communications can themselves trigger fail-safe actions, so thresholds for degraded operation must be defined; safety may force physical rather than logical separation (NIST s5.3; control SI-17) [H].

**Why a cloud/IT platform must not be (or look like) a safety function**
1. No bounded latency/availability (WAN, DNS, certificates, region, deploys) [L].
2. No independence: one multi-tenant codebase/pipeline/credential set both reads and commands (common cause) [L].
3. No systematic capability: SIFs need an IEC 61508 lifecycle and change control; continuous SaaS delivery is the opposite [L].
4. Real protective functions: Siemens SIMOCODE pro does pump dry-run protection in the motor starter (active-power undercut) and "fulfills the requirements of SIL 1 according to IEC 61508"; for sensor chains "proof of correct interaction and of compliance with SIL ... has to be individually executed by the plant operator" (Siemens white paper 2020, s5.1, s2.1) [H].
5. Audit findings (a)-(e): Greecon's guards are not engineered as protective functions.

**Recommended boundary**
- L0 hard-wired protection (E-stop, overload/thermal, pressure-switch trips, high-high level, dry-run relay) owned by the integrator; L1 local controller + Hand-Off-Auto; L2 Greecon edge (planned local guard; still NOT a SIF); L3 cloud (monitoring, advisory, supervised remote commands). Any hazard that can injure people or destroy equipment within the process safety time is handled at L0/L1 with zero dependency on L2/L3; Greecon takes no SIL/PL credit.
- Feature classes as UI badges: Advisory / Supervisory (mode or setpoint to a controller with its own protection) / Direct actuation / Safety function (never offered). Every command carries `executionMode: SIMULATED | LIVE` (today all SIMULATED).
- Wording: say "operating guards/limits", not "safety interlocks"; define GAIA's top tier as "operational safety priority (non-SIL)".
- Contract clauses (lawyer to finalise): intended use = monitoring, analytics, advisory, supervised remote operation, not a safety system; customer/integrator keeps independent protection and equipment fails safe without the platform; local control (HOA, E-stop, lock-out) prevails; data may be late/missing, platform shows age and quality; alerts are informational, no warranty to detect every hazard; published feature status ("commands currently simulated; nothing is written to equipment"); security/incident/support terms (D, F). Liability exclusions may not survive Directive (EU) 2024/2853 (software and cyber defects; transposition due 9 Dec 2026) [M: law-firm commentary, text not read]; accurate claims are the real protection.

## B) Safe command design - checklist with references
**B1. Direction rule (finding a).** Classify commands: SAFE-DIRECTION (stop, close, disable, de-energise, setpoint toward safe), HAZARD-DIRECTION (start, open, enable, increase), CONFIG/MODE. Process interlocks (over-pressure, low-flow, rest time, sensor quality, staleness) gate ONLY hazard-direction commands. Safe-direction commands face only authN/authZ, tenant scope, audit and a separate rate budget - never process state or data quality.
- Authority: Machinery Directive 2006/42/EC Annex I s1.2.4.1 (control device to bring machinery safely to a complete stop; energy to actuators cut once hazardous motion stops) [M, secondary sources]; its sentence that the stop control has priority over start controls, and s1.2.3 (start by voluntary actuation), are recalled, NOT verified [L-M]; carried into Reg. (EU) 2023/1230 Annex III (applies 20 Jan 2027) [M]; IEC 60204-1 s9.2 stop categories 0/1/2, emergency stop overrides all other functions [M, recalled]; NIST fail-to-known-state [H]. No water-sector-specific normative sentence found [L]; the logic is universal: permissives gate starts, trips drive to the safe state.
- Nuance: stops can have consequences (water hammer, lost aeration/disinfection/mixing): use a controlled local stop and a consequence warning, never a block.
- Tests: STOP accepted under over-pressure, dry-run risk, stale/BAD data, rate and rest limits; gateway offline = queued, visibly pending.

**B2. Start gating (finding b).** Each signal: quality, sourceTimestamp, maxAge. START only if every required input is Good and age <= maxAge at execution time (re-check at the edge, time-of-check/time-of-use); unknown = deny with reason. OPC UA vocabulary to copy (Part 8 s7.3.2) [H]: Uncertain_LastUsableValue ("Whatever was updating this value has stopped doing so"), Uncertain_NoCommunicationLastUsable (last good value, "currency is unknown"), Bad_NoCommunication, Bad_SensorFailure, Bad_OutOfService, Bad_WaitingForInitialData, Uncertain_SubstituteValue (manual overwrite), Uncertain_SimulatedValue, Uncertain_EngineeringUnitsExceeded, Good_LocalOverride. Suggested maxAge = 3 x publish period + latency budget (5 s pressure ~20 s; 60 s tank level ~4 min), set per asset template [L].

**B3. Dry-run in practice (finding c).** Dry-run = rotor turning without liquid. Flow = 0 is the normal state of a stopped pump, so low flow means nothing until the pump is confirmed running and a start-up bridge time has passed. Siemens: fixed 0.5 s start-up override, adjustable bridging 0-60 s (pumps are commonly started against a partly closed discharge valve), trip delay 0-10 s (default 0.5 s), trip level 1.1 x active power at minimum flow, no automatic restart after a trip; preconditions: pump pre-filled, PMIN/POPT < 0.80, fixed-speed direct-on-line motors (s3.3-3.4, s5.1) [H]. Sensors: suction level switch (bubble/vibration false alarms, no trip level, misses a closed suction valve), discharge flow (direct; delays/false alarms), discharge pressure (sees zero flow and blockage; bubble-sensitive) (s2.1) [H]; undercurrent relay example: pick-up 20-90% of rated current, 1-300 s delay [M, LK-EA vendor note]; float dry-run level: off after a delay, on after a second delay once level recovers [M, Wilo].
- So START permissive = suction side (level above minimum submergence/NPSH margin, suction pressure, suction valve open, primed, no latched low-low), never discharge flow (it deadlocks every start). RUN protection = trips in the motor controller (L0/L1). Redefine "dry-run risk" as `LOW_FLOW_WHILE_RUNNING` = running feedback true beyond bridge time AND flow < threshold AND data Good/fresh; running state unknown -> UNKNOWN. Show as advisory with a STOP recommendation; after a protective trip require human acknowledgement before restart for hazardous assets; auto-restart with hysteresis only by asset policy.

**B4. Envelope and lifecycle.** commandId (UUIDv7), idempotencyKey, targetAssetId, action, params, issuedAt, expiresAt, issuer, approvals[], expectedPriorState, preconditionSnapshot (value, age, quality), executionMode, cloud signature verified by the edge (CRA Annex I Part I(2)(f): protect integrity of "commands, programs and configuration" [H]). Set-state semantics ("desired=RUN"), not toggle. TTL: hazard-direction short (30-120 s [L]), never executed after expiry; stops persist until acked/cancelled; duplicate key returns the original result. States CREATED > APPROVED > SENT > RECEIVED > EXECUTED > CONFIRMED (process feedback) | FAILED | EXPIRED | CANCELLED | UNKNOWN. UI says "running" only after CONFIRMED; on reconnect reconcile desired vs reported (device-shadow pattern) [M]. MQTT: never retain commands (a retained START replays on reconnect); MQTT 5 Message Expiry Interval, QoS 1 + idempotency [M, recalled].

**B5. Confirmation by consequence.** T0 stop/close: one tap, undo, consequence note. T1 reversible start/open: confirm dialog listing preconditions. T2 asset-affecting (override a guard, change limits, bypass/discharge valve, dosing): reason + second approver + step-up auth + auto-expiry. T3 people-exposed hazards (mixers, conveyors, confined-space valves): no remote start. Select-before-operate with a timeout is the established two-step pattern (IEC 61850, DNP3) [M, recalled]. GAIA commands use the same path plus per-rule rate caps.

**B6. Rate limits** (min off-time, starts/hour, per-user rate; also enforced at the edge) apply to hazard-direction only; stops are de-duplicated, never limited.

**B7. Dead-man/lease.** Hazard-direction states are leases ("run until T" / "while heartbeat OK"); on expiry or comms loss the edge applies the asset's declared policy {STOP, CLOSE, HOLD, LOCAL_SCHEDULE}, chosen per asset because stopping can harm (reservoir starvation); NIST: define thresholds for operating with lost communications [H]. IEC 62443-3-3 SR 3.6 / 4-2 CR 3.6 "deterministic output": outputs go to a predetermined state when normal operation cannot be maintained due to an attack [M: recalled; secondary confirmation only].

**B8. Local precedence.** HOA local or lock-out engaged: platform refuses/cancels remote commands, shows "local control"; remote never overrides a lock-out. E-stop stays hard-wired; no software "emergency stop" button (ISO 13850) [M, recalled]. Manual override (reason + audit) bypasses guards: treat as T2 with expiry and a persistent banner.

**B9. Audit** every attempt (allowed/denied): actor, tenant, reason, guard result, input snapshot with ages, approvals, outcome, SIMULATED/LIVE.

**B10. Gate for the first real write:** B1 tests green; staleness + heartbeat live; edge-evaluated guard; signed commands; local-override state read; consequence tiers in the UI; integrator commissioning checklist + FAT/SAT evidence; independent L0 protection confirmed on site.

## C) Alarm and data-validity handling (bad/stale data, unknown state, heartbeat/offline)
- Rule: bad, stale or unknown data never displays as OK or as a number. Evidence (NUREG-0700 Rev.4, local 06-design-work/nureg0700r4.txt; nuclear HSI guidance = good practice, not law) [H]: 14.3-3 Invalid Data (indicate failed validation); 14.3-4 Unvalidated Data ("the unvalidated status of the data should be clearly indicated"); 14.3-5 quality indicator "valid, invalid, unvalidated"; unvalidated = "of unknown quality"; 14.4-2 alert personnel when automation fails to manual.
- Unknown is first-class: GOOD | UNCERTAIN | BAD | STALE | UNKNOWN (never received) | OVERRIDDEN | SIMULATED, computed at read time (`effectiveQuality` = f(quality, now - sourceTs vs maxAge, gateway liveness, range checks)). UI: hatched grey + "last good 14:02", never green, never 0; charts show gaps; aggregates exclude non-GOOD and show coverage % (compliance reports must disclose gaps). An alarm on a BAD/STALE point becomes "unknown"; it cannot clear because data vanished.
- Heartbeat/offline (finding e) [L: design]: edge heartbeat every 15-30 s (monotonic counter, version, uptime, buffer depth, per-device last good poll); liveness from server receive time, not the gateway clock; ONLINE > LATE (2 missed) > OFFLINE (3 missed, floor 60-120 s); OFFLINE forces all that gateway's signals to STALE; a scheduled server watchdog (not request-driven) flips state and raises "gateway offline"; after reconnect the backlog (edge buffer >= 72 h) is tagged `late-arrival` and excluded from real-time decisions; flag sourceTs beyond a skew tolerance.
- Live alerts (finding d): missing alarms are as dangerous as floods: the ASM deck cites Texas City (start-up authorised while key alarms were known not to work, 15 dead) and Pembroke (275 alarms in 11 minutes) [H as reported in local 06-design-work/honeywell-asm-2009.txt; not independently verified]. Minimal first set: gateway offline, signal stale, sensor bad, over/under-pressure (deadband + on-delay), LOW_FLOW_WHILE_RUNNING, starts/hour or runtime excess, override active > N h; each with owner, expected action, priority, auto-clear, escalation; no silent suppression. Rationalise per ISA-18.2/EEMUA 191 ("de-facto standard" per the deck [H]); roughly <= 1 alarm per 10 min per operator manageable [M, recalled].

## E) Device identity and transport; secure OTA; SBOM; vulnerability disclosure; patch SLAs
Sources marked "recalled" were not fetched this run.
- Per-gateway secret (SHA-256 in DB) is acceptable for pilots IF: random >= 128 bit (a fast hash is fine for high-entropy tokens [M]); constant-time compare; ingest-only scope bound server-side to gateway + tenant (never trust payload tenant IDs); shown once; per-gateway rate limit, last-seen/IP; rotation with overlap, instant revocation; root-only/keyring storage, not image or env; TLS >= 1.2 with validation. Residual risk: stolen PC/disk = stolen secret = spoofed telemetry and, later, intercepted commands.
- Target: mTLS with X.509 and a TPM 2.0 non-exportable key (IEC 62443-4-2 CR 1.2 [M]; CRA Annex I Part I(2)(d) [H]). Enrolment: single-use expiring bootstrap token bound to gatewayId -> CSR -> private-CA certificate (EST, RFC 7030 [M]); 30-90-day certs, automated renewal, server-side deny-list instead of CRL/OCSP; tenant resolved server-side; CA key in cloud KMS, offline root; monitor expiry (an expired cert is an availability incident).
- Seam: `GatewayCredential{type: secret|mtls, id, status, notBefore, notAfter, lastUsedAt}`. Need proven by: customer demand for device certificates, a fleet at unguarded sites, a secret-theft event, TPM hardware.
- MQTT: loopback-only Mosquitto is right; anonymous off, per-client ACLs, no cloud bridge without TLS + client certs; a LAN listener only with TLS + per-client credentials + topic ACLs; no retained commands [M, recalled; https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html].
- Time: NTP with NTS (RFC 8915 [M]), cross-check against cloud receive time, skew in the heartbeat, monotonic clocks for TTLs so a clock jump cannot revive an expired command; NIST SC-45 and s6.2.12 [H].

## F) Multi-tenant SaaS security and resilience
- Bug class: a missing tenant filter is broken object-level authorisation (OWASP API1:2023 [M, recalled]). Layers, cheapest first:
  1. Make the unscoped read unrepresentable: data access only via repositories that REQUIRE a `TenantScope` from the verified JWT (never params/headers); no global in-memory maps (caches are `Map<tenantId, ...>` behind one `TenantScopedStore`); an architecture/lint test bans raw stores/ORM outside repositories; jobs carry tenantId; ingestion binds gateway -> tenant server-side.
  2. CI gate of cross-tenant contract tests: tenants A and B with canary strings; enumerate EVERY route (lists, exports, aggregates, SSE/WebSocket, error bodies), call as B with A's IDs, assert 403/404 and no canary in any response; the build fails if a route lacks a registered test.
  3. Response guard: NestJS interceptor asserting every object with `tenantId` equals the request tenant (throw in test/staging, log + alert in prod).
  4. Postgres RLS backstop: ENABLE + FORCE ROW LEVEL SECURITY, policy `USING (tenant_id = current_setting('app.tenant_id')::uuid)`, non-owner app role without BYPASSRLS, `SET LOCAL` per transaction (pool-safe) [L: inference]. PG docs [H, https://www.postgresql.org/docs/current/ddl-rowsecurity.html]: superusers/BYPASSRLS and (unless FORCE) owners bypass; default-deny without policy; USING doubles as WITH CHECK; FK/unique checks bypass RLS (covert channel); TRUNCATE/REFERENCES exempt; policy expressions run before user functions except leakproof ones; `row_security=off` makes backups error rather than silently filter; the page says nothing on pooling or current_setting. TimescaleDB continuous aggregates/compression with RLS: UNVERIFIED, test first [L]. RLS cannot see in-memory reads (the bug found), so app-level scoping stays primary.
- Secrets: none in the repo (pre-commit + CI scanning); runtime injection from a secret manager (cloud KMS or SOPS + age); JWT keys with `kid` rotation; access tokens <= 15 min + rotating refresh with reuse detection; argon2id; MFA (TOTP/WebAuthn) mandatory for owner/admin (NIS2 21(2)(j) customers will ask [H]); separate prod admin identities.
- Tamper-evident audit: INSERT-only role + trigger blocking UPDATE/DELETE; per-tenant hash chain `hash = SHA-256(prev_hash || canonical_json(entry))`; anchor the head daily outside the DB trust domain (WORM bucket, signed email to the tenant owner, or RFC 3161 timestamp [M]) because a DB admin can rewrite an unanchored chain; verification CLI; `auditor` read-only; log reads of the audit log; retention >= 1 year [L].
- Backup/DR [L: suggested targets]: config/audit/command data RPO <= 15 min (WAL archiving/PITR), RTO <= 4 h; telemetry history RPO <= 1-24 h, RTO <= 24 h (edge buffers >= 72 h); encrypted, immutable, separate-account backups (3-2-1); quarterly restore drill with timings; a "pull the WAN cable" test (platform failure = loss of visibility, not control). NIS2 21(2)(c) makes backup/DR a customer duty [H].
- Incident response: one-page runbook (severity matrix, on-call, evidence preservation, notice templates, contact registry, yearly tabletop). Clocks [H, see D]: CRA Art 14 24 h/72 h/14 d or 1 month; NIS2 Art 23 24 h/72 h/1 month (customers); Albania Law 25/2024 4 h/72 h/1 month (designated operators); Law 124/2024 72 h to the Commissioner, processor tells controller immediately. Contract a 4-24 h customer notice depending on designation.

## H) Implications
**(i) MUST EXIST FROM DAY ONE (proven need)**
1. Safety-boundary text, badges (Advisory/Supervisory, SIMULATED/LIVE), "safety interlock" renamed, contract clauses - finding (a); liability exposure.
2. Direction taxonomy + stop-never-blocked, with regression tests - finding (a).
3. Signal model {quality, sourceTs, maxAge}, read-time effectiveQuality, fail-closed start gating, distinct stale/unknown rendering - findings (b), (e).
4. State-aware LOW_FLOW_WHILE_RUNNING + suction-side start permissive + bridge time - finding (c).
5. Gateway heartbeat + server watchdog + minimal live alerts - findings (d), (e).
6. Tenant-isolation guard (TenantScope repositories, CI cross-tenant tests, response guard) - the leak.
7. MFA for owner/admin, rate limits, append-only audit, secret scanning, scoped/rotatable gateway secrets - threats 1, 5, 10; CRA Annex I Part I(2)(d),(l).
8. security.txt + CVD policy + monitored contact, CI SBOM + dependency scanning, incident runbook with 4 h/24 h/72 h clocks, published support period, SRP access - CRA Art 14 live since 11 Sep 2026 (also for products already on the market); customer NIS2 questionnaires.
9. Backups with a tested restore; edge store-and-forward >= 72 h; WAN-unplug test - NIS2 21(2)(c) flow-down; resilience claim.
10. The no-real-write release gate (B10) on the roadmap - guard logic is not yet safe in front of actuators.

**(ii) SEAMS for later (extension point -> what proves the need)**
- `GatewayCredential` (secret | mtls) -> device-certificate demand, secret theft, TPM hardware, unguarded sites.
- Edge guard engine fed by a signed, versioned policy bundle sharing the cloud guard's schema -> first real-write request, or a comms-loss event that mattered.
- Command envelope + lease/TTL/ack machine (used even while simulated), per-asset comms-loss policy, HOA/lock-out status signal -> first pilot with a real actuator.
- `UpdateChannel` for signed OTA (TUF/RAUC/SWUpdate, cosign) -> first hardware shipment, many remote sites, CRA 11 Dec 2027.
- Postgres RLS -> any isolation-test failure, demand for DB-level isolation, a second dev team; `tenant.isolationTier` (pooled/bridge/silo) -> a utility needing a dedicated database/region.
- External audit-chain anchoring + log export (syslog/CEF) -> a regulated customer asks for non-repudiation/SIEM forwarding.
- Read-only ingestion of safety-system status (SIS trip/bypass as data, never control) -> demand for one pane of glass.
- IEC 62443-4-1 gap assessment/ISASecure, CRA technical file (Module A) or notified-body path, EU authorised representative -> procurement requirement, Art 7(4) outcome, first EU sale, 11 Dec 2027.
- Alarm KPIs/rationalisation tooling (flood detection, shelving) -> alarm load beyond one operator.

**(iii) THINGS TO AVOID**
- Any SIL/safety claim; "safety interlock" wording for cloud checks; a software E-stop; "prevents damage" marketing.
- A guard that blocks stop/close/disable; auto-restart after a trip or power return without checks; toggle commands; retained MQTT commands; commands without TTL; unbounded queues.
- Missing data as 0/OK/"last value forever"; free-text quality; sentinel numbers.
- Cloud-only protection, or any protective action that depends on connectivity.
- DIY crypto/PKI/OTA/auth; building a SIEM; multi-region Kubernetes; chasing IEC 62443/SIL certificates before a customer asks; accidentally adding Annex III functions (VPN, firewall, router, own OS image) to the edge product.
- Shared gateway secrets; secrets in repo/images; inbound ports, shared-account remote access or exposed Modbus/MQTT at sites.
- Global caches without a tenant key; "see all tenants" endpoints without strong gating; unguessable IDs as authorisation.
- Alerts for everything; silent suppression; claiming CRA/NIS2/62443 "compliant/certified" without evidence; presenting simulated results as executed; over-promising real-time/24x7; editable audit entries; an unanchored hash chain sold as tamper-proof.
